## Module 3: SGP4 and frames (`packages/core/test/sgp4Verification.test.ts`, `module3.test.ts`)

**Official SGP4 verification** (Vallado et al., AIAA 2006-6753; files from celestrak.org, copied unchanged into `packages/core/test/fixtures/`): all 32 propagation cases match the reference to within 1 m in position and 1 mm/s in velocity at every listed time; the error-code case 33334 is refused. Three things Claude found in the reference files are explained at the top of the test and in `docs/orbit-notes.md`. **Please read them**: they are the only places where the comparison is not one-to-one.

1. Case 23599 is compared with the Java reference, because the MATLAB 2015 reference differs from it by up to 0.96 km (this case is in the set to show the "Lyddane" disagreement). satellite.js matches the Java values to 1e-8 km.
2. Case 33334 (error-code test): the reference prints t = 0 and then stops with an error; satellite.js gives the error already at t = 0. The test checks that the elements are refused.
3. The last block of `tmatverDec2015.out` has a malformed line; only rows inside each TLE's requested time range are used.

**Question for the owner (SPEC.md 6.3 is [PROPOSED]):** with the proposed rules, inclined geosynchronous satellites (QZSS, BeiDou IGSO, old GEO satellites whose inclination has grown past 10°) come out as **MEO**, although they are at GEO altitude. Options: keep it; add a fifth class "IGSO"; or call anything with a period within 1 % of a sidereal day "GEO" whatever the inclination. Claude's suggestion: a fifth class "IGSO", since a GEO filter that hides them, or a MEO filter that includes them, would both surprise visitors.
